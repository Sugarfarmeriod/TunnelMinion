# 机主身份与访客权限：我的电脑自动互信，朋友按人配对

> 状态：已实现（#197、#199、#201、#202、#204、#205），2026-10-28 真机验收通过，记录见文末。总体方向见 [`node-agents.md`](node-agents.md)，配对现状见 [`model-borrowing.md`](model-borrowing.md) 的"邀请码"一节，代批准见 [`agent-fix.md`](agent-fix.md)。

## 一句话

每个机主有一把**机主密钥**。机主的每台电脑都由这把密钥签名，登记在一份**"我的电脑"名单**里；名单上的电脑自动互相信任，不用两两配对。朋友不再按电脑配对，而是**按人配对**一次，配好后朋友的电脑只能提问、看结论；批准修复、改设置只有机主自己的电脑能做。

## 为什么需要

- 现在两台电脑靠邀请码一对一配对。3 台电脑要配 3 次，5 台要配 10 次。
- 配对之后，每个对端都是一样的"对端"，分不清是我自己的电脑还是朋友的电脑。要靠逐台打开 `allow_delegation`、`allow_model_borrowing`、`allow_proxy_repair_approval` 这几个开关来区分，容易开错。
- 加了一台电脑或换了一台电脑，要去每台旧电脑上重新配一遍；淘汰一台电脑时，也要去每台电脑上删一遍。

## 四种身份

| 身份 | 是谁 | 能做什么 |
|---|---|---|
| 本机 | 坐在这台电脑前的人（本机网页只绑定 127.0.0.1，本机命令行） | 全部 |
| 我的电脑 | 和本机同一个机主、在"我的电脑"名单上的其他电脑 | 提问（委派）、看结论、借模型、远程调只读工具、**替本机批准修复** |
| 朋友的电脑 | 本机机主按人配对过的朋友，他名单上的电脑 | 只能提问（委派）、看结论；借模型要本机另外打开。**不能**批准修复，**不能**改设置，也不能远程调只读工具拿原始数据 |
| 其他 | 没配对过的电脑 | 什么都不能做，连本机的服务地图都看不见 |

**信任不传递**：我配了朋友，朋友配了他的朋友 X，X 和我之间仍然互相看不见。

## 基本做法

### 三把密钥

| 密钥 | 存在哪里 | 用来签什么 |
|---|---|---|
| 机主密钥（Ed25519） | 机主的第一台电脑的系统钥匙串里 | 只签三样东西："某台电脑属于我"的证书、"我的电脑"名单、"我信任的人"名单 |
| 电脑密钥（Ed25519） | 每台电脑自己的系统钥匙串里，从不离开这台电脑 | 只签这台电脑发出的请求 |
| 恢复密钥 | 不存在任何电脑上，只以一串恢复码交给机主自己保管（抄下来或存进密码管理器） | 只签一件事："换一把新的机主密钥" |

机主密钥只放在第一台电脑上，加电脑、删电脑都在这台电脑上操作；其他电脑丢了也不会泄露机主密钥。机主密钥本身丢了，靠恢复码救回来（见下文）。

钥匙串沿用现在网关凭据的存储方式（`KeyringSecretStore`，用户显式选择时用受限文件 `RestrictedFileSecretStore`），没有屏幕登录的 Mac mini 也能用。

**按用途区分签名**：每次签名都带上用途标签（例如 `tm-device-cert`、`tm-roster`、`tm-trust-list`、`tm-owner-rotate`、`tm-request`），验签时必须和预期用途一致。这样一个用途的签名不能被挪去冒充另一个用途。

### "我的电脑"名单

名单里有：机主密钥的指纹、恢复密钥的指纹、每台电脑的节点 ID、显示名、电脑公钥、组网地址和端口，以及一个**版本号**。整份名单由机主密钥签名。

- 每次加电脑、删电脑，版本号加一，重新签名。
- 每台电脑只接受签名正确、机主指纹和本机一致、而且版本号**比本机现有的大**的名单。旧版本、签名不对、别的机主签的，一律丢掉。
- 本机更新名单用 SQLite 的 `BEGIN IMMEDIATE` 短事务，"比较版本号 + 写入"一次完成，两份名单同时到达时不会互相覆盖。
- 名单的每次变化（谁加的、谁被移除、什么时候、原因）都写进本机的审计记录，不含任何密钥。

### 请求怎么认证

```mermaid
sequenceDiagram
    participant A as 电脑 A（请求方）
    participant G as 电脑 B 的 Gateway（服务所在的电脑）
    A->>A: 用电脑密钥签一张短期通行证<br/>（发给 B、用途、60 秒内有效、一次性编号、A 手上的名单版本）
    A->>G: 请求 + 通行证
    G->>G: 在 B 自己的名单里找 A 的公钥，验签
    G->>G: 用 B 本机的数据决定 A 是"我的电脑"还是"朋友的电脑"
    G->>G: 按身份查权限表；再看本机对 A 的开关
    G-->>A: 允许或拒绝
    Note over A,G: 如果 A 的名单版本比 B 新，B 先向 A 要新名单
```

- **权限只在服务所在的那台电脑上判断。** 请求里没有"我是机主"这种字段；即使有，也一律忽略。B 只看两件事：通行证是不是由 B 本机名单里的某把电脑公钥签的；这把公钥属于 B 的机主，还是属于 B 配过的某个朋友。
- 通行证只对指定的那台电脑、指定的用途有效，60 秒过期；验证时容许两台电脑的时钟相差 2 分钟以内，家用电脑之间差十几秒很常见。一次性编号在有效期加上这段误差之内只能用一次，截获了也没法拿去别处重放。这比现在长期有效的配对令牌更安全。一次性编号只记在内存里，所以网关重启后大约 3 分钟内，同一张通行证还能再用一次；但它只能从签发它的那台电脑的组网地址发出，也只对同一台电脑、同一类接口有效，这个风险可以接受。
- 现在的配对令牌（静态令牌）继续能用，见下文"迁移"。

### 加一台我的电脑

```mermaid
sequenceDiagram
    participant N as 新电脑
    participant O as 持有机主密钥的电脑
    O->>O: tunnelminion owner invite → 一次性加入码（含机主指纹）
    Note over O,N: 机主把加入码带到新电脑
    N->>N: 生成电脑密钥（存进钥匙串）
    N->>O: 报到：加入码 + 电脑公钥 + 用新密钥签的应答
    O->>O: 原子消费加入码；用机主密钥签证书；名单版本 +1
    O-->>N: 证书 + 新名单
    N->>N: 核对名单上的机主指纹和加入码里的一致
    O->>O: 把新名单推给名单上其他在线的电脑
```

- 加入码沿用现在邀请码的规则：24 小时有效、只能用一次、本机只存摘要、报到来源地址必须和报上来的地址一致、失败时统一回答"无效、已过期或已被使用"、报到每分钟最多 10 次。
- 加入码里带着机主指纹，新电脑据此确认自己加入的是对的机主，组网里有人冒充也骗不过去。
- 新电脑报到时要用新密钥签一段应答，证明私钥确实在它手里。

### 移除一台我的电脑

在持有机主密钥的电脑上运行 `tunnelminion owner remove <电脑>`：名单版本加一，去掉那台电脑，重新签名，推给所有在线的电脑。被移除的电脑如果在线，也会收到通知并删除自己的证书；但这只是顺手做，安全不依赖它。

### 和朋友按人配对

- 我在持有机主密钥的电脑上运行 `tunnelminion friend invite`，朋友在他持有机主密钥的那台电脑上运行 `tunnelminion friend join <配对码>`（双方都要把对方写进自己签名的"我信任的人"名单）。配好后，机主可以用 `friend rename` 在本机给朋友改显示名，不必沿用对方自己报上来的名字。
- 双方交换的是**机主公钥和各自的"我的电脑"名单**。配好后，朋友名单上的所有电脑都被我的所有电脑认作"朋友的电脑"，朋友那边同理。
- "我信任的人"也是一份由机主密钥签名、带版本号的名单，和"我的电脑"名单一样在我的电脑之间同步。所以朋友只需配一次，不用跟我的每台电脑分别配。
- 朋友能看到我名单上的全部电脑，每台电脑各自决定朋友能做什么。
- 朋友加了新电脑、删了电脑，他的新名单会在两边电脑接触时同步过来（规则同上：签名对、版本更大才收）。
- 解除配对：`tunnelminion friend remove <朋友>`，从"我信任的人"名单里删掉他，版本加一并同步。

## 设计里要回答的问题

### 1. 离线电脑错过了"移除某台电脑"的通知

例子：电脑 C 被移除时，电脑 B 关着机。B 开机后手上还是旧名单，旧名单里 C 仍然是"我的电脑"。

处理分两层：

1. **一接触就同步。** 每张通行证里都带着请求方手上的名单版本。B 开机后，只要和任何一台我的电脑或朋友的电脑说上话，发现对方版本更新，就先要来新名单再处理请求。B 自己开机后也会主动找名单上的其他电脑同步一次。
2. **被移除的电脑没法帮 B 更新。** C 手上只有旧名单，它的请求里带的也是旧版本，所以 B 不会从 C 那里学到"C 还在"之外的东西。只要 B 和任何一台其他电脑接触过，C 就会被拒绝。

剩下的风险是：B 还没来得及和任何其他电脑同步时，C 仍能做它被移除前本来能做的事。TunnelMinion 只跑在机主自己组的网里，被移除的电脑一般是机主自己淘汰的，这个风险可以接受。被盗或丢失的电脑应该走下面的"换机主密钥"，而不是只移除。

### 2. 机主密钥丢了怎么恢复

| 情况 | 怎么办 |
|---|---|
| 持有机主密钥的电脑坏了，恢复码还在 | 在任意一台我的电脑上运行 `tunnelminion owner recover`，输入恢复码。恢复密钥签发"换成新的机主密钥"声明，新机主密钥存进这台电脑的钥匙串，名单用新密钥重新签名、版本加一。其他电脑认得恢复密钥的指纹（它从第一天起就写在名单里），所以会自动接受新机主密钥，朋友那边也一样。不用重新配对。 |
| 持有机主密钥的电脑被偷了 | 同上。新名单里顺手把被偷的电脑移除。旧机主密钥签的东西从此一律不收，小偷拿着旧密钥也签不出更大版本的有效名单。 |
| 恢复码也丢了 | 没法证明"我还是原来那个机主"，只能重新开始：选一台电脑 `owner init --reset` 生成新的机主密钥和恢复码；其他每台电脑要有人**在本机**运行一次 `owner join` 重新加入；朋友要重新配对一次。旧配对在此之前照样可用，不会突然断掉，只是不能再加电脑、删电脑。 |

`owner init` 和 `owner recover` 会显示恢复码，并要求机主把整串恢复码再输一遍，确认已经抄下来。恢复码不进任何日志、数据库或 Git。

### 3. 和现有功能的关系、怎么平滑迁移

| 现有功能 | 以后怎么样 |
|---|---|
| 邀请码 `invite` / `join`（`agent/invites.py`） | 保留，作为"旧式配对"继续工作。新的 `owner invite` 和 `friend invite` 复用它的一次性加入码存储（`SQLiteInviteStore`：只存摘要、一条 `UPDATE … RETURNING` 原子消费）、来源地址核对和统一错误文案。 |
| 对端开关 `allow_delegation`、`allow_model_borrowing`、`daily_quota` | 变成"按身份的默认值 + 本机收紧"。我的电脑默认全部打开；朋友默认只开"允许提问"，借模型默认关闭、额度沿用 20 万。每台电脑仍可以在本机为某个朋友或某台电脑单独关掉或调小，但**不能**为朋友打开下面这条。 |
| 代批准 `allow_proxy_repair_approval`（#193） | 我的电脑默认允许替本机批准（本机可以关掉）；朋友的电脑**永远不允许**，配置里打开也无效，网关检查身份时直接拒绝。动手的仍是服务所在电脑，动手前照样再核对。 |
| 远程调只读工具（`allowed_tools`） | 我的电脑照旧；朋友的电脑不再能直接调，只能通过委派拿结论。 |
| 改设置 | 现在只能在本机网页或本机命令行改，这一版不变，也不新增远程改设置的接口。规则先写进权限表：以后如果加远程改设置，只限"我的电脑"。 |

**迁移步骤**（全程不断线）：

1. 两台电脑升级以后，旧的静态令牌配对照样能用，界面上标成"旧式配对"。旧式配对的权限就是现在配置文件里那几个开关，行为和今天完全一样。
2. 机主在一台电脑上运行 `owner init`，再在其他电脑上 `owner join`。加入以后，两台电脑之间优先用新的通行证认证；旧令牌还在，作为后备。
3. 运行 `tunnelminion peers migrate`：本机列出所有旧式配对，对已经在"我的电脑"名单上的，提示删掉旧令牌；对剩下的（一般就是朋友），提示改用 `friend invite` 重新按人配对。不自动删除任何东西，每一条都要机主确认。
4. 这一版不停用旧式配对，也不设强制下线的期限。

### 4. 协调服务器里哪些能复用，哪些要新写

协调服务器（`src/tunnelminion/coordinator/`）已经冻结，这次**不重新启用它，也不改那个目录**。新代码放在新模块 `src/tunnelminion/trust/`，按需借用做法：

| 内容 | 处理方式 | 说明 |
|---|---|---|
| 一次性加入令牌 | 复用现有邀请码存储 | `SQLiteInviteStore` 已经是"只存摘要 + 原子消费"，比协调服务器的 `enrollment_tokens` 更贴近现在的用法 |
| 加盐哈希 + 常量时间比较（`_hash_secret` / `_matches_secret`） | 照做法新写一份 | 只用在加入码摘要上；直接从冻结目录 import 会把两边绑在一起 |
| `BEGIN IMMEDIATE` 短事务 | 照做法新写 | 用在名单版本比较和写入上 |
| Ed25519 签名、按用途（audience）验签、短期通行证（`identity.py` 的 `AssertionService`、`OfflineAssertionVerifier`） | 照做法新写 | 协调服务器是"服务器签、节点验"，这里是"每台电脑自己签、对方按名单验"，签名者和信任来源不同，只沿用 PyJWT 的 EdDSA、`aud`、过期时间和时钟容差这些做法 |
| 移除审计（`coordinator_audit`、`revoke_node`） | 照做法新写 | 表结构参考：谁、对谁、做了什么、版本号、原因，不含秘密 |
| 钥匙串存储（`SecretStore` 及两种后端） | 直接复用 | 已经在 `model/secrets.py`，不属于协调服务器 |
| 网关认证入口（`GatewaySecurityPolicy.authenticate`） | 扩展 | 现在依次尝试"静态令牌"和"协调服务器断言"；增加第三种"电脑通行证"，认证结果多带一个身份字段（本机机主 / 朋友 / 旧式） |
| 权限检查（`gateway/api.py` 里各接口对开关的判断） | 改成查一张权限表 | 身份决定上限，本机开关只能在上限以内收紧 |
| 组网、心跳、目录同步、托管模式 | 不用 | 名单同步走现有 Gateway，只在电脑之间点对点交换 |

## 节点编号冲突与已知限制

- **节点编号只能属于一个身份。** 朋友的名单里如果写了我某台电脑的节点编号，整份名单都不收。如果写的是另一个朋友某台电脑的编号，名单照收：要是整份拒收，一个朋友抢先占了另一个朋友新电脑的编号，就能让那个朋友以后的名单更新（包括移除被偷的电脑）一直进不来。撞号的那个编号，两边谁都不认，审计里记一笔，`friend list` 里也会标出"编号冲突，暂不认"。
- **和旧式配对撞号时，以旧式配对为准。** 朋友名单里的编号和本机某个旧式配对相同、但地址不同时，旧式配对照常可用，朋友冒用这个编号签的通行证不认，出站请求也不会被改投到朋友的地址。
- **托管模式（协调服务器）的节点不参与撞号检查。** 托管模式已经冻结、目前没有在用；以后如果重新启用，要把托管节点也纳入检查。
- **换密钥后要尽快让所有电脑同步。** 换完密钥，旧恢复码就作废了，要立刻销毁。还没同步的电脑仍然认旧恢复码；这段时间旧恢复码一旦泄露，别人就能对这些电脑另换一把机主密钥，让它们和其他电脑分叉。
- **只装了朋友配对那一版的电脑，要先升级才能接受机主换密钥。** 旧版本不认换密钥声明，会继续用旧机主密钥验证名单。
- **"曾经是我的电脑"的记录从这一版开始才有。** 本机只记下升级后收到的"我的电脑"名单里出现过的节点；升级前就已经被移出的电脑不在记录里。机主身份是这一版才有的功能，升级前并没有这样的电脑，所以实际上没有影响。

## 怎么算做完

**自动测试要覆盖：**

- 签名用途不符、机主不符、版本号更小或相同的名单一律拒收；两份名单并发写入只留版本更大的那份。
- 通行证过期、发给别的电脑、用途不符、一次性编号重复使用，都被拒绝。
- 请求里自称"机主"、或者朋友的电脑出示了伪造的"我的电脑"证书，都被拒绝；权限只按服务所在电脑本机的名单判断。
- 朋友的电脑：配置里打开 `allow_proxy_repair_approval` 也无法批准；不能直接调只读工具；能委派、能拿到结论。
- 没配对过的电脑：所有接口都认证失败；朋友的朋友同样如此。
- 离线电脑：开机后与任意一台电脑接触就拿到新名单并拒绝被移除的电脑。
- 恢复：用恢复码换机主密钥后，其他电脑和朋友自动接受，旧机主密钥签的名单被拒收。
- 旧式配对：升级后行为与今天一致；`peers migrate` 不经确认不删除任何东西。
- 任何日志、数据库、错误信息里都没有私钥、恢复码和令牌明文。

**真机验收**用这台 Windows 电脑和 Mac mini。"第三台电脑"（`.data/c`，端口 8788）和"朋友"（`.data/f`，端口 8789）放在另一台电脑上，或者这台电脑上的单独数据目录里。Mac 访问不了自己的组网地址，所以这两个角色不能放在 Mac 上。下面的命令都在仓库目录里运行；`<PC 数据目录>`、`<Mac 数据目录>` 是两台电脑平时用的数据目录（用默认位置时可以省掉 `--data-dir`），`<PC 组网地址>`、`<Mac 组网地址>` 是两台电脑的 WireGuard 地址，`<C 组网地址>` 是放"第三台电脑"和"朋友"的那台电脑的地址（放在这台电脑上时就是 `<PC 组网地址>`）。

**准备**：两台电脑都更新到最新的 `main`，运行 `uv sync`。验收前两台电脑之间已经有旧式配对。每启动一个网关就单独开一个终端，验收结束再按 `Ctrl+C` 停掉。

1. **建立机主身份，Mac 加入"我的电脑"**
   - 这台电脑：`uv run tunnelminion owner init --data-dir <PC 数据目录>`。把显示的恢复码抄下来，按提示完整输入一遍。
   - 这台电脑：`uv run tunnelminion owner invite --data-dir <PC 数据目录>`，记下 `tmo1_` 开头的加入码。然后启动网关：`uv run tunnelminion gateway --data-dir <PC 数据目录>`。
   - Mac：`uv run tunnelminion owner join <加入码> --data-dir <Mac 数据目录>`。然后重启 Mac 的网关：`uv run tunnelminion gateway --data-dir <Mac 数据目录>`。
   - 检查：两边运行 `uv run tunnelminion owner status --data-dir <数据目录>`，都列出 2 台电脑、名单版本相同；网页设置页里，对方标为"我的电脑"。在这台电脑上运行 `uv run tunnelminion peers migrate --data-dir <PC 数据目录>`，能看到原来那条旧式配对，回答 `n` 保留。
2. **第三台电脑只和这台电脑打交道**
   - 这台电脑：再运行一次 `owner invite`，拿到新的加入码。
   - 放"第三台电脑"的那台电脑：`uv run tunnelminion owner join <加入码> --data-dir .data/c --bind-host <C 组网地址> --bind-port 8788`，然后 `uv run tunnelminion gateway --data-dir .data/c`。
   - 检查：`uv run tunnelminion owner status --data-dir <Mac 数据目录>` 列出 3 台电脑；Mac 的地图上出现"第三台电脑"，在 Mac 上点"问问"，能把问题委派给它。Mac 和第三台电脑之间没有做过任何配对。
3. **我的电脑之间默认可以代批准**：按 [`agent-fix.md`](agent-fix.md) 里的办法，让 Mac 本机提出一个修复（例如停掉一个被观察的 Docker 容器）。在这台电脑的地图上点 Mac 头上的感叹号批准，Mac 动手修好。这一次没有运行 `peer-proxy-approval`。
4. **离线的电脑上线后同步到移除**
   - 停掉 Mac 本身的网关（`.data/c` 的网关保持运行）。
   - 这台电脑：`uv run tunnelminion owner remove <第三台电脑的节点 ID> --data-dir <PC 数据目录>`。输出里应该提示"这次没推到"Mac。
   - 重新启动 Mac 的网关，等十几秒。
   - 检查：`uv run tunnelminion owner status --data-dir <Mac 数据目录>` 只剩 2 台电脑；`uv run tunnelminion owner status --data-dir .data/c` 显示本机已被移出；Mac 的地图上不再有第三台电脑。Mac 的审计里有这次移除，可以用 `sqlite3 <Mac 数据目录>/runtime.sqlite3 "select payload from trust_audit order by sequence desc limit 3"` 查看。
5. **朋友按人配对，只能提问、看结论**
   - 放"朋友"的那台电脑：`uv run tunnelminion owner init --data-dir .data/f --bind-host <C 组网地址> --bind-port 8789 --display-name 朋友的电脑`，然后 `uv run tunnelminion gateway --data-dir .data/f`。
   - 这台电脑：`uv run tunnelminion friend invite --data-dir <PC 数据目录>`，记下 `tmf1_` 开头的配对码。
   - 放"朋友"的那台电脑：`uv run tunnelminion friend join <配对码> --data-dir .data/f`。
   - 检查：两边 `friend list` 都能看到对方。朋友的网页用 `uv run tunnelminion --data-dir .data/f --port 8767` 启动，在那台电脑上打开 `http://127.0.0.1:8767/`。朋友的地图上能看到这台电脑和 Mac；向 Mac 提问能拿到结论；Mac 再提出一个修复时，朋友那边点批准会被拒绝。朋友不能直接调只读工具，这一条由自动测试覆盖。
6. **没配对过的电脑什么都做不了**：在这台电脑的 PowerShell 里运行 `curl.exe -s -o NUL -w "%{http_code}" -H "Authorization: Bearer a.b.c" http://<Mac 组网地址>:8787/v1/capabilities`，应返回 `401`。
7. **用恢复码换机主密钥**
   - Mac：`uv run tunnelminion owner recover --data-dir <Mac 数据目录>`，按提示输入第 1 步抄下的恢复码，再把新显示的恢复码完整输入一遍。
   - 检查：这台电脑的 `owner status` 显示机主指纹已经换成新的，并且"本机持有机主密钥：否"；Mac 的 `owner status` 显示"本机持有机主密钥：是"。朋友那边运行 `uv run tunnelminion friend list --data-dir .data/f`，仍然列着我，而且没有重新配对。这台电脑和 Mac 之间照常互相看得见、能委派。旧恢复码随即作废，要立刻销毁。

验收记录只写示例地址和节点 ID 的缩写，不写真实 IP、机器名、令牌和恢复码。

## 真机验收结果（2026-10-28）

基于 `main` 的 `9b2170a`。实际布置和上面的步骤有一处不同：Mac 访问不了自己的组网地址，所以"第三台电脑" C 和"朋友" F 都放在这台 Windows 电脑上，各用一个单独的数据目录和端口，而不是放在 Mac 上。第 1～7 步全部通过。

1. **建立机主身份、Mac 加入**：两边的 `owner status` 都列出 2 台电脑，名单版本一致；网页设置页里对方标为"我的电脑"。`peers migrate` 能看到原来的旧式配对，回答 `n` 后保留。
2. **C 只和这台电脑打交道**：三方名单一致（版本 5），Mac 的地图上出现了 C，Mac 把问题委派给 C 成功，C 返回了本机服务概况。Mac 和 C 之间没有做过任何配对。
   这一步发现并修好了一个真实问题：通行证原来只容许 5 秒的时钟误差，而 Mac 的时钟比这台电脑快大约 11 秒，Mac 签的通行证一律被拒（401）。#205 把误差放宽到 2 分钟；一次性编号的缓存一直保留到过期时间加这段误差，所以可重放的时间没有变长。
3. **我的电脑之间默认可以代批准**：Mac 的 Agent 查出一个测试容器停了，提出"重启容器"。在这台电脑上批准后，Mac 执行前再核对一遍，然后重启容器、自己验证通过（修复状态成功，标记为由对端批准，验证通过）。全程没有运行 `peer-proxy-approval`，本机收紧设置一条都没有。
4. **离线的电脑上线后同步到移除**：停掉 Mac 的网关后，这台电脑执行 `owner remove C`，输出提示"这次没推到 Mac，下次接触时会同步"。重启 Mac 的网关，大约 30 秒后 Mac 的名单变成版本 6、只剩 2 台。C 的 `owner status` 显示"本机已被移出我的电脑，已停止使用通行证"，Mac 的地图上也不再有 C。
5. **朋友按人配对**：F 用 `owner init` 建立了自己的机主身份，`friend invite` / `friend join` 成功。两边的 `friend list` 都能看到对方，这台电脑和 Mac 都在朋友那边的名单里，权限是可以提问、不能借模型、每日额度 20 万。F 向 Mac 提问拿到了结论。Mac 再提出一个修复时，F 查看修复只得到"不允许"、看不到详情；F 去批准，被 Mac 拒绝（403，"没有允许这台电脑替它批准修复"）。
6. **没配对过的请求**：带伪造的令牌、或者不带令牌访问 Mac 网关的 `/v1/capabilities`，都返回 401。
7. **用恢复码换机主密钥**：在 Mac 上用第 1 步的恢复码执行 `owner recover` 成功，旧恢复码作废。Mac 显示"本机持有机主密钥：是"，这台电脑显示"否"；两边的机主指纹都换成了同一把新的，名单版本 7。F 那边自动换成了新的指纹，没有重新配对。换密钥之后，这台电脑委派给 Mac 照常成功。

验收结束后，停掉了全部临时网关和网页，关掉了临时开放的端口，删掉了两台电脑上的验收数据目录和测试容器。

**验收中发现、尚未处理的问题**（已记进路线图的"以后再说"）：

- 对方认证失败（401）时，`/api/peers` 里的"可达"仍然显示为是，容易误导。
- 第 4 步里，Mac 的审计只记了"从某节点同步名单，版本 6"，没有直接写出移除了哪台电脑。
- 朋友的地图把朋友自己这台电脑也列成了一个"我的电脑"对端。
- 朋友那边显示我的名字时，用的是这台电脑的电脑名（"这台电脑"），对朋友来说容易混淆，应该改用机主的显示名。
- 本机的 Qwen 小模型在可用工具很多时，容易不去调用 Docker 工具；换成 DeepSeek，或者在问题里点名工具后就正常了。

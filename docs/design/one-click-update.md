# 一键更新

> 状态：已实现（合并即发布、只核对 sha256、只留最近 10 个 Release）。真机验收结果见文末。

## 解决什么问题

现在换版本要五步：去 GitHub Actions 登录、找一次成功的 CI、下载压缩包、解两层包、`stop` 再 `start`。
三台电脑每台都要做一遍；Windows 还必须在桌面上做，否则读不到凭据管理器。

做完以后：本机网页"设置"里能看到"当前版本 / 最新版本"，点"更新"、确认一次，等一两分钟页面自己回来，
就是新版本。新版起不来会自动退回旧版。也可以用一条命令 `tunnelminion update` 做同样的事。

```mermaid
flowchart LR
    ci[合并到 main 后 CI 构建运行包] --> rel[发布到 GitHub Releases<br/>附带 sha256 清单]
    rel --> check[主人打开设置页<br/>查看有没有新版本]
    check --> click[主人点更新并确认]
    click --> dl[下载 校验 解包<br/>放进新的版本目录]
    dl --> swap[独立的换包进程<br/>停旧版 启动新版]
    swap -- 新版健康 --> done[完成 保留旧版一份]
    swap -- 新版起不来 --> back[自动停掉新版 启动旧版]
```

## 新版本从哪来

CI 产物要登录 GitHub 才能下载，程序拿不到。所以加一步：**合并到 `main`、CI 全部通过以后，自动把两个平台的
运行包发布成一个 GitHub Release**。仓库是公开的，Release 不用登录就能下载。

- 每个 Release 的名字是 `build-<CI 运行序号>`，例如 `build-512`，说明里写对应的提交。
- 附件：`tunnelminion-windows-amd64.tar.gz`、`tunnelminion-macos-arm64.tar.gz`、`release.json`
  （每个附件的大小和 sha256、对应提交）。
- 只保留最近 10 个 Release，更早的由 CI 自动删掉（连同 tag），避免列表越堆越长。
- 程序只认这个仓库：地址写死在代码里，不能通过网页或配置改成别的地址。测试时可以用环境变量指向
  `127.0.0.1` 上的本机测试源，别的地址一律拒绝。

**怎么判断"更新"。** 运行包里的版本号一直是 `0.1.0`，真正能比新旧的是提交。程序拿自己运行包清单里的提交，
和最新 Release 的提交，问一次 GitHub 的提交比较接口：

- 最新 Release 在当前提交之后 → 显示"有新版本"。
- 相同 → "已是最新"。
- 当前比最新 Release 还新（自己构建的开发版）或者两边分叉 → 不提示更新，只显示"当前是未发布的构建"。
- 比较接口不通（例如 GitHub 匿名限额用完）→ 显示最新版本号，但标"无法确认是否比当前新"，仍可手动更新。

只在主人打开设置页或点"检查更新"时才联网，不在后台定时检查。

每次合并到 `main` 且 CI 全部通过都会自动发布，合并完二十分钟左右三台电脑都能看到新版本。

## 怎么确认包没被篡改

两层都必须通过，任何一层不通过就删掉下载的东西、不换包：

1. **整包 sha256。** 下载完先核对大小和 sha256，必须和 `release.json` 里写的一致。
   防的是下载断了、被代理改了、被换了。
2. **逐文件 sha256。** 解包以后，用现有的运行包检查（`verify_runtime_package`）逐个核对清单里每个文件的
   摘要，多一个文件、少一个文件都不行；还要核对平台和 CPU 对得上。这一步手动安装时也在做。

另外：只从 `https://` 下载，解包时拒绝绝对路径、`..`、符号链接和特殊文件。

**不做签名，取舍如下。** 上面两层的"正确答案"和包本身放在同一个 Release 里，所以"包没被篡改"的保证等于
"GitHub 上的 Release 没被人动过"，最终靠 GitHub 账户本身的安全（两步验证）。签名能把"谁能发出更新"再收紧到
"持有私钥的人"，但要额外管理一把放在 GitHub Secrets 里的私钥；而拿到仓库写权限的人同样能让 CI 用这把私钥
签他的包。对目前三台自己的电脑来说，收益不抵维护成本，所以只核对 sha256。

## 怎么换

### 新版本放在哪

新版本不覆盖旧文件，而是放进本账户的程序目录里一个新的版本子目录：

- Windows：`%LOCALAPPDATA%\TunnelMinion\TunnelMinionRuntime\node-<数据目录摘要>\versions\pkg-…`
- Mac：`~/Library/Application Support/TunnelMinionRuntime/node-<数据目录摘要>/versions/pkg-…`

`node-<数据目录摘要>` 让同一台电脑上不同数据目录的实例（例如测试实例）各管各的，互不影响。程序目录和数据目录
不能重叠，现有代码已经强制检查。

第一次一键更新时，会把**当前正在运行的这一版**也复制一份进来，作为可以退回的旧版。以后版本目录里始终保留
"当前版"和"上一版"两份，更早的在不运行时自动删掉。

### 换包的步骤

本机网页本身就是要被停掉的那个进程，它不能自己给自己换包。所以分两段：

1. **网页进程做准备**（这期间旧版照常可用，随时可以取消）：下载到 `.part` 临时文件 → 核对整包大小和 sha256 →
   解包到临时目录 → 逐文件核对 → 移进 `versions/`。
2. **独立的换包进程做切换**：网页用**当前这一版（已知能跑）的可执行文件**启动一个脱离网页进程的换包进程
   （`tunnelminion update-apply`，不建服务、不建计划任务），然后网页回一句"正在重启"。换包进程不依赖新版能
   不能跑起来，所以新版就算完全坏掉也能退回。换包进程：
   1. 停掉旧版的本机网页和网关（沿用 `runtime stop` 的逻辑：只停能证明归属的进程，不强杀）。停不干净就不换，
      用旧版把已停的组件拉回来，记录"没有换包"。
   2. 把"当前版本"指针改成新版，运行新版自己的 `runtime start`（启动前检查、健康检查并稳定 2 秒都照常做）。
   3. 新版健康 → 结束，记录"已更新到 build-512"。
   4. 新版起不来 → 停掉新版残留进程，指针改回旧版，用旧版启动，记录"已退回，原因：startup_timeout"。
   5. 结果写进数据目录里的更新记录，页面回来后显示。

页面在第 2 段会断开一会儿，前端自动等本机网页重新可用后刷新，显示结果。

命令行 `tunnelminion update` 走同一套代码：先显示当前和最新版本，问一次 `y/N`，然后做第 1 段，
再在前台直接做第 2 段（命令行进程本身不是要被停掉的组件），打印结果。`tunnelminion update --check` 只查不换，
`--rollback` 退回上一版。

### 重启电脑以后用哪一版

以前的用法是手动运行解包目录里的 `tunnelminion runtime start`。更新以后新版在版本目录里，如果还去运行旧的
解包目录，就又回到旧版了。所以：**从这一版开始，`runtime start` 会先看本数据目录对应的"当前版本"指针，
指针指向别的版本时，自动转交给那个版本去启动**，并在输出里提示新版本所在的路径。这样老习惯照样能用，
起来的一定是最新换上去的那版。（这一转交逻辑只有包含本功能的版本才有，所以第一次要手动换到这一版。）

### Windows 的文件占用

- 正在运行的程序文件从不被覆盖或删除：新版放新目录，旧版目录原样留着当退回用。
- 清理更早的版本时，如果文件还被占用（例如杀毒软件在扫），跳过，下次更新再清。
- 换包进程从运行中的网页进程派生，和它在同一个桌面登录会话里，所以新版仍能用凭据管理器；
  换包进程会脱离网页进程所在的作业对象，网页被停掉时不会连带结束。
- 用命令行 `tunnelminion update` 时，如果是通过 ssh 远程执行的，Windows 上会提示"请回到这台电脑的桌面上运行"，
  因为 ssh 会话里起来的新版读不到凭据管理器。网页上点不受影响（网页本来就是从桌面启动的）。

### Mac 在哪个会话里启动

- 秘密已经改存在 `~/.tunnelminion/secrets/secrets.json`，从 ssh 启动也能读，所以换包不再要求桌面会话。
- 换包进程继承正在运行的旧版所在的会话，新版和旧版在同一个会话里。
- 程序自己下载的文件不带"来自互联网"的隔离标记，新版不会被系统拦一下要你点"打开"。
- 唯一的例外：从钥匙串时代的老版本第一次升级上来时，那一次搬家要在桌面上点弹框（见使用说明），
  一键更新只适用于已经升级过的版本，碰不到这个情况。

## 谁能点

- **只有本机主人在本机网页上能点。** 更新接口挂在只监听 `127.0.0.1` 的本机网页上，沿用现有的请求守卫：
  Host 必须是本机环回地址，写请求必须同源并带 TunnelMinion 请求头，所以别的网页也没法在你浏览器里偷偷触发。
- **其他电脑和朋友不能触发。** 网关不提供任何更新接口；Agent、MCP 都没有更新工具；"允许替我批准修复"
  也不覆盖更新。
- **预览模式不能更新**，按钮直接不显示。
- **从源码运行时不能更新**（例如 `uv run tunnelminion`），页面提示"从源码运行，请用 git pull"。
- **换包前确认。** 点"更新"后弹确认框，写清从哪个版本换到哪个版本、会中断一到两分钟、失败会自动退回。
  请求里必须带上刚才检查到的那个版本号，和服务器上再查到的最新版本对不上就拒绝，防止点的和换的不是同一个。
- 同一时间只能有一次更新在进行。

## 不做什么

- **不做后台静默自动更新**，也不在后台定时检查。每次都是主人自己点。
- 不做开机自启，不建系统服务、计划任务或登录项（和现在的 `runtime start` 一致）。
- 不做增量更新、断点续传：下载断了就删掉重下。
- 不支持选择任意历史版本安装；只能"更新到最新"或者"退回上一版"（命令行 `tunnelminion update --rollback`）。
- 不更新别的电脑。三台电脑各自在自己的本机网页上点。
- 不动数据目录和秘密存储：换的只有程序文件。

| 测试 | 校验失败（摘要不符、大小不符、多文件、路径越界）、下载中断、新版起不来自动退回、并发更新被拒、非本机请求被拒 |

- 单元测试：`tests/update/` 覆盖查版本（各种 GitHub 返回、限流、地址必须 https）、下载中断、大小或摘要不符、
  恶意压缩包（绝对路径、`..`、链接、多余文件）、逐文件校验失败、换包成功、新版起不来自动退回、退回也失败、
  旧版停不干净、并发更新被拒、跨站请求被拒、`runtime start` 转交；分支覆盖率 100%。
- 前端：`UpdatePanel.test.tsx` 覆盖确认框、进度、失败说明、重启后显示结果。
- 真机（用 PR CI 构建的两个平台运行包；"新版"由它改包 ID 和提交号派生，"坏的新版"再把标准库压缩包换成
  垃圾并同步清单摘要，能过校验但起不来；发布源是只监听 127.0.0.1 的本机测试源；测试实例用独立端口、数据目录和
  安装目录，Mac 上另把 `HOME` 指到测试目录，不碰真实的秘密文件）：

  | 场景 | Windows | macOS（从 ssh 操作） |
  |---|---|---|
  | 检查更新 | 显示有新版本 | 显示有新版本 |
  | 更新到坏的新版 | 新版起不来，自动退回原版，网页断开约 6 秒，全程约 23 秒 | 同样自动退回，全程约 22 秒 |
  | 更新到好的新版 | 成功，网页断开约 5 秒，全程约 17 秒；只留当前版和上一版 | 成功，全程约 18 秒 |
  | 更新后再检查 | 已是最新 | — |
  | 从旧解包目录 `runtime start` | 自动转交给新版启动 | 自动转交给新版启动 |
  | 命令行 `update --rollback --yes` | 退回上一版 | 退回上一版 |
  | 网页按钮完整流程 | 确认框 → 正在重启 → 显示新版本和"刷新页面" | — |

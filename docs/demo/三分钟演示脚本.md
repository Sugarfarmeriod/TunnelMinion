# TunnelMinion 三分钟演示脚本

目标观众是不熟悉 Agent 框架的项目所有者。演示只展示只读诊断、证据和故障隔离，不展示或输入
API Key、Gateway token、Authorization 头、WireGuard 私钥、完整进程列表或容器正文。

## 演示前准备

1. Windows A 的本机面板监听 `127.0.0.1:8765`。
2. macOS B 的 Tool Gateway 监听 `10.77.0.1:8787`。
3. 两端模型状态均为 `available`。
4. 预先打开 [Figma 架构图](https://www.figma.com/board/8KODvoNqXZsLCHKO0J4nbU)。
5. 预先打开 [真实双机人工验收](../guide/真实双机人工验收.md) 和两份 JSON 报告。
6. 录屏前关闭包含密钥、终端历史或无关应用内容的窗口和通知。

## 0:00–0:30：一句话和边界

画面：Figma 架构图。

旁白：

> TunnelMinion 是运行在 WireGuard 私网两端的只读诊断助手。FastAPI 接收请求，LangChain 让
> Qwen 选择允许的检查工具，但真正的系统读取由固定 Python 工具执行；安全策略拥有最终决定权。
> 它没有 Shell，也不会改端口、容器、路由或 WireGuard 配置。

必须指到的图中节点：A 本地 FastAPI、A Agent、B Tool Gateway、Qwen、本机 SQLite/密钥环。

## 0:30–1:05：本机聊天与确定性证据

画面：Windows `/chat`，打开已有的 `get_node_summary` 对话。

操作：指出用户问题、模型回答、`permission_denied` 和程序生成的证据索引。

旁白：

> 这里 Qwen 用两轮完成一次只读调用。WireGuard 接口确实已启动，但普通账户看不到 peer 统计，
> 所以系统明确显示权限降级，而不是编造连接细节。最下面的 tool run ID 由程序生成，可以回查。

备用素材：[Windows 聊天截图](../assets/acceptance/windows-chat.png)。

## 1:05–1:50：A 发现并探测 B 的服务

画面：打开 `ab-cross-node-diagnostic-2026-07-18.json`，只展示开头摘要和 `diagnostics`。

操作：依次指出 80、443、5984、8888 四项，以及 `unavailable_sources`。

旁白：

> A 先认证 B，再读取 B 的 Docker、进程和监听证据，然后由 A 自己探测端口。真实结果是 5984
> 和 8888 可达，80 和 443 不可达。Mac 无权列出完整监听，所以置信度保持为 low。Docker 的
> IPv4/IPv6 通配发布会合并成一个逻辑服务，不会把一次 IPv4 探测重复算成两份证据。

强调：不把 `unreachable` 解释成服务一定停止，只能证明 A 的 TCP 探测失败。

## 1:50–2:30：模型故障不会拖垮工具层

画面：打开 `model-failure-isolation-2026-07-18.json`。

操作：按顺序指出 503、资源 success、远端 Gateway success、恢复后的 200。

旁白：

> 我们临时移除了 A 的模型配置。新 AI run 正确返回 503，但本地资源仍是 200，A 仍能调用 B
> 的只读 Gateway。脚本在 finally 中恢复原 Qwen 配置，AI run 随后恢复 200。模型层、资源层和
> 跨节点工具层没有被绑成一个单点故障。

## 2:30–3:00：安全与工程结论

画面：GitHub PR Checks 绿色结果，随后切回 Figma 图。

旁白：

> 当前 216 个自动测试通过，源代码与分支覆盖率 100%，Windows 和 macOS GitHub Actions 都是
> 绿色。仓库扫描不包含 API Key、Gateway token、Bearer 凭据或私钥。MVP 仍严格只读；只有未来
> 真正加入写操作和人工审批时，才需要显式编写更复杂的 LangGraph 状态机。

结束字幕：`Evidence first. Read-only by construction.`

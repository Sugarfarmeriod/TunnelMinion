# ADR-0002：工具风险与执行边界

- 状态：Accepted
- 日期：2026-07-18

## 背景

模型需要读取真实 Windows/macOS 状态，但它生成的名称和参数都不可信。通用 Shell、Python
REPL 或运行时动态导入虽然灵活，却会把“读状态”扩大成任意代码执行，无法可靠证明 WireGuard、
路由、服务和容器保持不变。

## 决策

每个工具使用 `ToolDefinition` 声明稳定名称、协议版本、输入/输出 JSON Schema、平台、权限、
超时、最大结果、数据敏感级别和以下风险等级之一：

- `read-only`：MVP 唯一可向模型暴露的等级；
- `requires-approval`：当前不暴露，未来必须进入显式审批工作流；
- `forbidden`：禁止注册到模型工具集合。

名称只能精确匹配显式注册项，不做相似名称猜测、动态导入或命令拼接。模型参数在平台调用前
通过 Schema 校验。真正的系统读取由预先编写的固定适配器完成；Runtime 统一应用超时、取消、
并发、结果大小、审计和结构化错误。

远端网关再次应用只读允许列表。通过本机策略不代表自动获得对端权限。

## 被否决的方案

- 通用 Shell 或 Python 工具：权限范围无法静态描述，参数注入面过大。
- 只依靠系统提示禁止写操作：模型输出不是授权机制。
- 遇到未知名称时猜测最相近工具：会把编造行为转换成真实调用。
- 先执行再根据日志判断是否只读：不能撤销已经发生的副作用。

## 后果

- 新能力需要显式契约、适配器和测试，开发速度低于通用命令工具。
- 确定性边界可以独立测试；模型失败、提示注入或编造工具时不会扩大权限。
- MVP 不具备“顺手修复”能力。诊断可以建议后续人工方案，但不得声称已经修改系统。
- 未来引入写操作时必须新建 change，使用 `Plan → Policy Check → Human Confirm → Execute → Verify`
  的显式流程，不能把现有只读等级改名后复用。

# ADR-0004：跨节点应用认证

- 状态：Accepted
- 日期：2026-07-18

## 背景

WireGuard 能证明流量来自私有隧道中的 peer，但不能表达“哪个 TunnelMinion 节点可以调用哪些
工具”，也不能代替应用层撤销、限流和审计。MVP 只有两个预配节点，不需要先建设 OAuth、PKI
或中心控制面，但不能复用 WireGuard 私钥作为应用凭据。

## 决策

MVP 使用显式 peer 配置和每 peer 独立的高熵 `tmn_` Bearer token：

- token 与 WireGuard 密钥格式和生命周期分离，不进入非秘密 JSON 配置；
- 默认保存在操作系统密钥环；无交互 macOS 环境只有用户显式选择时才使用权限为目录 `0700`、
  文件 `0600` 的受限文件存储，不静默降级；
- Gateway 启动时读取 token，立即转为 SHA-256 摘要；请求认证使用常量时间比较；
- 配置与 Web/API 视图只报告 `credential_configured`，不返回明文或摘要；
- Gateway 只绑定明确的私有 WireGuard 地址，拒绝环回、通配、公网和多播地址；
- 认证成功后仍要检查调用节点、精确工具允许列表、版本、参数、每 peer 限流、超时和响应预算；
- 撤销 peer 同时删除非秘密配置和所属应用凭据，不修改 WireGuard 配置。

A/B 审计使用相同 `run_id` 和 `tool_run_id` 关联一次调用，但不记录 Bearer token、认证头或工具
敏感正文。未认证请求也记录无秘密安全事件。

## 被否决的方案

- 只依靠 WireGuard peer 身份：缺少工具级授权和独立撤销边界。
- 复用 WireGuard 私钥：扩大高价值密钥暴露面并耦合两个生命周期。
- 把共享 token 写入普通 JSON 或环境导出：容易进入日志、备份和评估报告。
- MVP 立即建设 OAuth 2.1/mTLS 控制面：对两个静态节点过重；不妨碍后续在规模扩大时迁移。

## 后果

- 首次配对需要在两端安全预配独立 token；当前版本不自动发现或分发凭据。
- Bearer token 一旦泄露，需要撤销并重新预配；它不是短期签名凭据。
- 私网绑定和应用认证必须同时成立，不能用其中一个替代另一个。
- 节点数量、动态授权或第三方客户端增加时，应重新评估 mTLS、短期签名 token 或标准 OAuth
  资源服务器，而不是继续扩大静态共享 token 的使用范围。

## Context

当前后台观察任务在 FastAPI lifespan 启动期间立即拍首张快照，而 Uvicorn 的本机面板端口稍后才开始监听。全新数据目录因此会在后续确认窗口把面板自身识别为 `service_added`，与 Windows/macOS 首次启动不得产生启动 incident 的既有规格不符。

调查循环首轮设置了 `require_tool_call=true`，但 OpenAI-compatible 后端可能返回结构有效、没有工具调用的 `insufficient_evidence`。当前 Runtime 只在该响应结构无效时执行本机只读兜底。2026-09-05 的 macOS 正式包重复验证得到 0/3 工具命中和 0/3 证据化结论，证明合法无工具响应在本机服务场景中虽然安全，却没有用户价值。

## Goals / Non-Goals

**Goals:**

- Windows 与 macOS 全新数据目录首次启动时，把应用自身监听纳入初始基线，不创建启动 incident 或调用模型。
- 本机观察产生的服务 incident 在第一次模型响应未选择工具时，先通过现有 Tool Runtime 获取一次监听证据，再允许模型结束调查。
- 工具失败、模型失败和证据不足继续形成保守终态；所有现有预算、审计、参数校验和证据门槛保持有效。
- 远端、Coordinator 目录和聚合来源绝不执行本机兜底。

**Non-Goals:**

- 不改变模型 Provider、模型服务或提示词，不增加重试层和新依赖。
- 不增加工具，不执行 Shell、Python 或任何网络与系统写操作。
- 不处理 packet relay、复杂 Provider、自动组网、showcase、WireGuard、防火墙、路由或 DNS。

## Decisions

1. **后台观察循环在首个周期结束后再拍第一张快照。** 这样 Uvicorn 与同期开机服务已经进入稳定集合，第一张完整快照直接成为基线。相比按 PID 或端口排除 TunnelMinion，这不需要把 Web 端口耦合进服务观察器，也不会从资源视图隐藏应用自身。代价是启动后的一个观察周期不产生 incident；这与“先建立完整基线”的既有语义一致。

2. **只对 `local_observation` 来源的服务对象执行首轮确定性取证。** 当 `tool_calls == 0` 且尚未执行工具时，Runtime 使用既有 `list_network_listeners` 定义构造一次兜底调用。无论首轮无工具响应的结构有效与否，都先取得实时监听证据；节点对象继续沿用现有“仅无效结构才兜底”的行为。

3. **一次兜底后恢复现有模型循环。** 工具结果仍经过 schema、平台策略、超时、结果大小和审计边界；模型可继续选择 `get_process_summary`，也可基于已有证据形成结论或安全结束。Runtime 不伪造结论，也不把工具成功等同于根因确认。

4. **保留远端证据隔离。** 非 `local_observation` 来源即使首轮没有工具或格式无效，也不得运行本机工具。结构有效的证据不足报告可保留；结构无效则按现有失败路径结束。

5. **真实验收使用正式 CI 包和隔离监听。** Windows/macOS 各运行 5 个全新数据目录样本，只创建非特权临时监听并通过 SQLite 只读观察结果。总计至少 8/10 取得 `list_network_listeners` 成功证据、至少 7/10 形成引用工具证据的结论，且无无证据确认、禁止工具执行或场景无关工具调用。

## Risks / Trade-offs

- [启动后一个周期内新增的服务会被视为初始基线] → 明确把该窗口定义为启动稳定期；基线建立后的变化仍使用两次确认规则。
- [确定性监听调用仍可能失败或返回部分结果] → 复用现有 Tool Runtime 状态与证据规则，失败时保持 `insufficient_evidence`，不补写推测。
- [模型服务偶发不可用会降低实机通过率] → 门槛允许少量失败，但不在本阶段增加重试或改动模型服务；超出容忍度时保留失败证据。
- [本机服务首轮比以前多一次工具调用] → 仅在模型违背首轮工具要求时触发，且固定为与服务事件直接相关的只读监听工具。

## Migration Plan

无数据迁移或 API 迁移。发布新包后观察调度和调查行为自动生效；回滚只需恢复上一正式包，现有 SQLite 数据仍兼容。

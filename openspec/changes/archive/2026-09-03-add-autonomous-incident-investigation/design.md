## Context

现有 Runtime 已提供六个结构化只读工具、Coordinator 节点/服务完整快照与新鲜度、统一 Context Runtime、证据引用、Overview 和审批操作状态机。缺口不是继续增加工具，而是把这些能力组成一个低干扰产品循环：后台确定性观察，重要变化形成 incident，一个 Agent 在预算内调查，用户从总览查看结论并追问。

本 change 横跨后台调度、持久化 Agent 状态、Overview API/React 和评估，因此需要统一数据边界。所有新能力仍只在本机运行；Coordinator 与远端工具结果继续视为不可信输入。

## Goals / Non-Goals

**Goals:**

- 用可重复的规范化快照差异识别重要变化，正常刷新不消耗模型。
- 用一个可恢复、受预算约束的 Investigation Agent 收敛候选根因和证据。
- 让 Overview 直接展示 incident 状态、调查轨迹、结论、未知项与追问入口。
- 用固定故障矩阵和量化指标判断该产品循环是否真的有用。
- 复用现有工具、目录、上下文、证据、对话和操作审批模型。

**Non-Goals:**

- 不引入多 Agent、Reviewer、规划器层级、通用事件总线或新的模型框架。
- 不允许模型生成或执行 Shell/Python，不新增网络 Provider、relay 或写工具。
- 不在普通刷新时调用模型，不自动处理 incident，不改变任何操作授权。
- 不建设公共 SaaS、企业 RBAC、全网日志平台或通用 AIOps。

## Decisions

### 1. 快照差异是确定性领域逻辑

后台从现有本机资源与 Coordinator 服务目录构造有界规范化快照。快照只保留稳定身份、状态、来源、新鲜度和观测时间，不保存业务响应正文。比较器输出固定事件类型：服务新增、服务消失、节点离线、状态陈旧、仅本机可用、远端不可达。相同对象、类型和基线修订生成稳定去重键；重复刷新更新最后观测时间，不重复启动调查。

选择这一方案是因为现有目录已提供完整快照与新鲜度，无需再造消息总线或让模型比较 JSON。固定触发规则可测试、无 token 成本，也能在模型不可用时继续工作。

### 2. 每个 incident 最多运行一个 Investigation Agent

incident 保存一个结构化调查状态：候选假设、每项状态与依据、证据引用、已调用工具、剩余预算、停止原因和公开摘要。每轮模型只能从当前允许的六个只读工具中选择下一项，Runtime 校验工具和参数后执行，再把结果作为新证据回填。模型不获得任意代码、写工具或操作审批能力。

同一 incident 不并发启动第二个 Agent；新证据进入当前状态或在终止后形成后续调查。先采用单 Agent 是最小可验证方案；只有固定评测证明存在上下文、并行或独立复核瓶颈时，才另建 change 讨论 Reviewer 或多 Agent。

### 3. 停止条件由 Runtime 强制，结论按证据分级

Runtime 在以下任一条件满足时停止：一个根因达到规定证据门槛且不存在冲突关键证据；必要证据不可获得；模型/工具轮次、调用数、墙钟或上下文预算耗尽；用户取消；模型或运行时失败。最终报告固定区分已确认事实、候选解释、未知项、停止原因和证据引用。无证据断言不得被保存为确认结论。

这复用现有 Context Runtime 的预算和实时证据优先级，不新增第二套推理运行时。隐藏思维链不保存；调查轨迹只记录公开假设状态、工具动作和证据结果。

### 4. Incident 是 Overview 的一等只读资源

服务端提供有界 incident 列表与详情读模型；Overview 显示活动/近期 incident 卡片，详情显示公开轨迹、结论、未知项和动态建议问题。追问创建或继续一个绑定 incident 的现有 conversation thread，自动注入该 incident 的有界公开上下文；它不复制完整工具结果，也不改变原 incident 结论。

不新建聚合后端或独立聊天产品：扩展现有 Overview 聚合契约并复用 conversation/runtime。建议问题由当前 incident 的未知项和可用下一步确定性生成；模型生成文案只能作为有界增强，失败时仍显示固定问题模板。

### 5. 调查与处理保持硬边界

Investigation Agent 只能观察和报告。用户要求处理时，系统根据已有证据进入现有 Plan → Confirm → Execute → Verify → Rollback/Cleanup 流程，并重新执行当前策略和证据校验。incident 成功不构成授权，也不自动创建 operation。

### 6. 先用固定矩阵证明单 Agent 价值

离线矩阵至少覆盖：服务新增、服务消失、节点离线、目录陈旧、环回监听导致仅本机可用、远端不可达、Docker 不可用、必要工具失败、模型失败和预算耗尽。报告计算根因成功率、工具选择率、非必要调用率、无证据断言率、失败恢复率与端到端延迟，并保留每个失败的可审计分类。

真实 A/B 只读评测是后续发布证据，不是开始实现的前置条件；不得用写网络或反复人工提权补足离线矩阵。

## Risks / Trade-offs

- [快照噪声造成 incident 风暴] → 只比较规范化字段，使用稳定去重键、确认窗口和并发上限；阈值由固定场景验证。
- [模型把相关性误写成根因] → 确认结论必须满足证据门槛，报告保留未知与候选状态，并计入无证据断言率。
- [远端状态陈旧导致错误调查] → 保留来源、新鲜度和观测时间；陈旧本身是事件，不能作为当前事实。
- [模型或工具失败留下半成品] → 持久化公开状态和预算，终止为明确失败/信息不足；不自动重放远端工具。
- [Overview 信息过载] → 首页只显示活动与近期重要 incident，完整轨迹在详情中按需展开。

## Migration Plan

1. 先增加快照、差异和 incident 存储，以只记录模式运行，确认正常刷新零模型调用且去重稳定。
2. 接入单 Agent 状态循环和固定离线矩阵，默认只对测试触发源启用。
3. 扩展 Overview 读模型、incident 页面与上下文追问，再启用本机真实只读观察。
4. 通过固定门禁后，才允许在明确配置的私有网络节点启用自动调查；关闭开关即可退回现有 Overview 与手动聊天。
5. 本 change 不迁移或删除已有 conversation、operation、memory、目录或历史 change 数据。

## Open Questions

- 首轮默认观察周期、确认窗口和 incident 保留期由离线噪声测试确定；它们必须有界且可在本机配置，但不扩展为通用规则引擎。

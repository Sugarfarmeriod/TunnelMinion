## Context

TunnelMinion 当前没有实现代码。本 change 需要同时建立协调服务、跨平台 Agent、WireGuard 数据面、服务目录和本地 Web UI，主要风险集中在跨平台权限、节点身份、NAT 环境下的连接质量以及自动发现的准确性。

目标用户首先是愿意自托管协调节点、设备数量较少且成员互相信任的个人或小团队。协调节点通常位于具有稳定公网地址的服务器上，但它自身也可以运行 Agent 并作为普通服务提供节点出现。

必须覆盖 Windows、macOS、Linux。三端的网卡管理、系统服务、端口到进程映射和凭据存储机制不同，因此共享核心与平台适配层必须在项目开始时分离。

当前已有可复用的真实环境：开发机 A 运行 Windows，通过官方 WireGuard 客户端连接家庭 macOS 设备 B；B 使用手写 WireGuard 配置和终端命令承担服务器角色，同时自身也是网络节点。A/B 已经互通，因此首个原型应先以只读方式观察现有隧道，再使用独立测试接口验证自动管理，避免破坏正在使用的连接。

项目所有者熟悉 Python，并明确希望优先使用 Python 降低实现门槛。当前 Windows 环境已有 Python 3.11 与 3.12 可用，首版核心运行时以 Python 3.11+ 为兼容基线。

## Goals / Non-Goals

**Goals:**

- 交付从节点注册、网络配置、连通到面板展示的最小端到端闭环。
- 节点优先建立点对点 WireGuard 路径，并在直连不可用时通过协调节点保持可用性。
- Agent 无需大模型 API 即可自动生成基础服务目录。
- 每个节点通过仅监听本机的 Web UI 获得一致的操作体验。
- 建立可测试的网络 Provider、平台适配器和服务探测器边界。
- 让故障状态可观察，使用户能区分注册失败、组网失败、服务过期和协调节点离线。

**Non-Goals:**

- 不实现 n2n 或同时运行多个数据面。
- 不实现细粒度服务可见性、访问 ACL 或多租户隔离。
- 不自动发布只监听 `127.0.0.1` 的服务，也不开放远程管理面板。
- 不实现大模型增强、完整游戏识别、UDP 服务代理或自动升级。
- 不扫描节点所在物理局域网，也不执行侵入式漏洞或协议扫描。
- 不在本 change 中承诺最终安装包形态或托管控制服务。

## Decisions

### 1. 分离协调服务、Agent 核心、平台适配和内嵌 Web UI

仓库采用单体仓库组织，但运行时保持清晰边界：

- `coordinator`：注册、身份、地址分配、节点状态、网络配置和服务目录。
- `agent`：节点生命周期、控制通道、网络 Provider、服务发现和本地 API。
- `platform`：Windows、macOS、Linux 的网卡、进程枚举、系统服务和安全存储适配。
- `web`：由 Agent 托管的静态前端，只调用本机 API。
- `protocol`：版本化的控制消息、错误码和共享数据模型。

Agent 与协调服务使用 Python 3.11+ 作为首版共同语言。共享核心使用类型标注、异步 I/O、明确的协议模型和平台适配接口；网络配置等高权限操作隔离在小型适配器中，避免业务层直接拼接系统命令。Web UI 与 Python 核心保持 API 边界，首版优先选择易调试、易打包的轻量方案，具体前端技术通过最小原型确定。

Python 的优势是开发者熟悉、原型速度快且三端生态成熟；代价是单文件分发、后台服务安装、原生依赖和高并发性能需要额外验证。性能敏感组件未来可以在不改变协议和 specs 的前提下替换或下沉，但 MVP 不提前引入多语言复杂度。

被否决的方案：首版分别为三端开发原生桌面应用。该方案会重复实现大量网络与生命周期逻辑，并显著拖慢最小闭环验证。

### 2. Agent 使用单一出站控制通道

Agent 主动连接协调服务，并通过带版本的 TLS 控制通道完成注册、心跳、网络配置和服务目录同步。Agent 不为控制面暴露公网监听端口；本地面板 API 仅绑定环回地址。

控制协议必须支持幂等快照或带修订号的状态更新，使断线重连后能够收敛。具体采用流式 RPC、WebSocket 还是长轮询属于实现选择，阶段 0 通过原型确定；外部行为不依赖具体传输库。

被否决的方案：协调服务定期主动连接每个 Agent。该方案要求节点开放入站端口，在 NAT 和个人设备环境中不可靠。

### 3. 使用设备密钥建立稳定身份

首次加入时，用户向 Agent 提供协调地址和短期 enrollment token。Agent 在本机生成设备密钥对，仅把公钥和必要注册信息发送给协调服务。协调服务签发稳定节点身份并分配虚拟地址；Agent 使用受平台保护或严格文件权限保护的本地存储保存凭据。

token 必须可撤销、可过期，并且不能作为节点的长期身份。节点名称可修改，但节点 ID 和虚拟地址在正常重新连接时保持稳定。

被否决的方案：所有节点共享一个长期预共享密钥。泄露后无法单独撤销节点，也无法可靠区分设备。

### 4. WireGuard 通过 Provider 边界管理

Agent 核心只依赖 `NetworkProvider` 能力：创建/删除网络、应用 peer 配置、读取状态和报告诊断。首个 Provider 为 WireGuard；平台差异封装在 Provider 与 platform 适配层内。

首版 Provider 优先调用各平台已安装的 WireGuard 工具和系统服务，而不是用 Python 重写 WireGuard 协议。Windows 适配器先兼容官方 WireGuard 客户端与 tunnel service；macOS 适配器先兼容 B 当前配置文件及终端启停流程。Linux 适配器在 A/B 闭环稳定后补充。

Provider 必须区分三种模式：只读观察用户已有接口、导入用户明确选择的配置、管理带 TunnelMinion 所有权标识的独立接口。默认从只读观察开始；只有用户明确授权后才能导入或创建配置。任何删除、覆盖或重写操作都只能作用于 Provider 自己创建并记录所有权的资源。

阶段 0 仍需分别验证三端所需权限、系统 WireGuard 依赖和 Python 调用系统工具的行为。未经实验，不预先承诺三端使用完全相同的驱动或命令路径。

被否决的方案：直接把 WireGuard 命令拼接散落在业务代码中。该方案难以测试，也会阻碍未来 n2n Provider。

### 5. 点对点优先，MVP 使用可信协调节点作为回退路由

协调服务交换 peer 所需的候选端点，Agent 对可用直连路径进行探测并优先选择直连。若在限定时间内无法建立可用直连，协调节点作为 WireGuard 路由节点提供回退路径。

MVP 的路由式回退意味着协调节点处于受信任边界，可能看到经其转发的解密后 IP 流量元数据或内容。UI 必须清楚标识 `direct` 与 `relayed` 状态。后续可以独立设计不解密内容的包中继，但不作为当前 change 的隐含承诺。

被否决的方案：首版只支持直连。该方案会使常见 NAT 失败直接表现为产品不可用。另一个被否决方案是首版自研完整的透明加密中继协议，其复杂度会掩盖核心闭环验证。

### 6. 服务目录使用被动枚举加有限安全探测

Agent 周期性枚举本机监听端口，并尽可能关联进程信息。Docker 可用且用户授予只读访问时，Agent 读取容器名称、镜像、标签和端口映射。主动探测仅限明确允许的低风险行为，例如读取 HTTP 响应头或协议握手元数据，并设置严格超时和并发预算。

服务记录至少包含稳定 ID、节点 ID、传输协议、监听地址、端口、可访问性、来源、推测类型、显示名称、最后观测时间和置信度。只监听环回地址的服务可以显示，但必须标记为仅本机且不得向远端提供可点击访问链接。

服务快照通过控制通道同步，协调服务使用 TTL 标记过期数据。不得采集文件内容、网络请求正文、容器环境变量或其他不必要的敏感数据。

被否决的方案：通过扫描整个端口范围识别本机或局域网服务。该方案成本高、误报多，也突破了用户对本地 Agent 的安全预期。

### 7. 面板由本地 Agent 聚合数据

Web UI 仅绑定 `127.0.0.1` 和 `::1`，随机或可配置端口由 Agent 管理。浏览器只与本机 Agent 通信；Agent 返回本机缓存的协调状态、节点列表、连接路径和服务目录。

HTTP/HTTPS 服务在确认可从虚拟网络访问时显示“打开”操作；其他服务提供复制 `host:port` 的操作。所有来自远端的名称和描述在 UI 中按不可信文本处理，禁止注入 HTML 或命令。

被否决的方案：所有用户直接打开协调服务上的集中式管理 UI。该方案弱化了本地优先体验，也会增加公网管理面的认证和攻击面。

### 8. MVP 状态存储与可观察性

协调服务使用单实例持久化存储保存节点身份、地址租约和必要配置；服务在线状态允许通过带 TTL 的记录重建。初始实现可选择嵌入式数据库，但存储访问必须通过仓储边界隔离，避免未来扩展被具体数据库锁死。

Agent 和协调服务输出结构化日志，并对节点状态、当前连接路径、最近错误和服务扫描时间提供稳定诊断模型。日志必须隐藏 enrollment token、私钥、大模型密钥和完整认证头。

## Risks / Trade-offs

- [三端 WireGuard 管理方式差异超出预期] → 在业务实现前完成三端最小实验，保持 Provider 接口不依赖单一驱动。
- [Agent 自动化破坏现有 A/B WireGuard 配置] → 首轮默认只读，使用独立测试接口与配置目录；修改前记录所有权和快照，拒绝删除未由 TunnelMinion 创建的资源。
- [Python 打包或原生依赖导致三端安装复杂] → 从项目开始建立干净环境构建测试，隔离平台依赖，并把单文件打包视为待验证目标而非前置承诺。
- [NAT 环境导致直连成功率低] → 明确探测超时、提供可信路由回退，并在诊断中展示路径与失败原因。
- [路由式中继扩大协调节点信任边界] → 文档和 UI 明示，默认自托管；将不解密内容的中继作为后续独立 change。
- [自动发现泄露敏感服务信息] → 只采集最小元数据，不扫描局域网、不读取正文，并允许停用 Docker 或主动探测来源。
- [端口和进程关联需要较高权限] → 权限不足时降级为仅端口信息，而不是阻止 Agent 运行。
- [服务名称误识别] → 保存来源与置信度，优先展示可验证元数据；没有大模型时保持确定性降级。
- [协调服务成为单点故障] → Agent 缓存最近有效配置，短时离线不主动拆除已工作的隧道；管理变更和目录新鲜度明确降级。
- [范围仍然过大] → 任务按纵向验收点推进，先完成两个同平台节点，再扩展三端和服务发现。

## Migration Plan

这是新项目，不存在数据迁移。实施按以下顺序逐步启用：

1. 建立 Python 工程、协议、身份和状态模型，完成无真实网卡的模拟端到端测试。
2. 以只读模式读取 A 的 `HomeMac` 隧道和 B 的现有配置，验证状态模型与本地面板，不改变现有接口。
3. 在 A/B 上使用独立的 TunnelMinion 测试接口启用 Provider，验证 Agent 创建、连接和完整清理。
4. 增加协调节点回退路径和连接状态展示。
5. 增加服务发现、目录同步和本地 UI。
6. 补充 Linux Provider，并分别完成 Windows、macOS、Linux 安装权限与清理验证后，才发布预览版。

回滚时停止 Agent 并调用 Provider 清理本 change 创建的虚拟接口、路由和临时配置；协调服务保留身份数据以供诊断，但旧客户端可被显式撤销。任何失败都不得删除用户已有的 WireGuard 接口或系统网络配置。

## Open Questions

- Python 依赖管理、可执行文件打包和后台服务安装最终采用哪些工具，需要阶段 0 原型确认。
- Python Provider 在 Windows WireGuard tunnel service 和 B 当前 macOS 启停方式下可安全实现哪些只读与写入操作，需要 A/B 实测确认。
- 控制通道最终采用哪种传输和序列化格式，需要根据代码生成、浏览器无关性和调试体验选择。
- MVP enrollment token 由 CLI 生成还是由本地管理页生成，尚未确定。
- 协调节点回退路由的默认带宽限制和并发上限，需通过性能测试确定。
- Docker Desktop、rootless Docker 和原生 Docker 的发现权限差异，需分别验证。
- 服务目录的默认扫描周期与离线 TTL，需在原型中平衡实时性、功耗和噪声。

# TunnelMinion AI-native 产品愿景与长期路线图

## 产品定义

TunnelMinion 是一个运行在私有组网节点上的分布式 AI Agent 系统，面向个人设备、家庭服务器和小型实验室。每个节点上的 Agent 能够通过大模型理解用户意图，通过受控工具感知本机及远端节点的网络、服务、容器和游戏状态，并通过上下文与记忆完成跨节点诊断、建议和经过审批的操作。

一句话定位：

> 让私有网络中的每台设备都拥有一个能感知环境、调用工具、彼此协作并安全执行操作的 AI Agent。

## 部署与所有权边界

产品按以下使用形态逐步发展，不把公共 SaaS 作为当前目标：

1. **当前正式目标：单所有者私有网络。** 同一位用户拥有 Windows、macOS 和家庭服务器等节点；每个节点仍独立保存秘密、权限策略和操作记录。
2. **未来扩展：家庭或小型实验室多人共享。** 每个节点具有明确所有者；请求者可以提出操作，但目标节点所有者的本地策略拥有最终授权权。
3. **远期可选：企业受管部署。** 需要独立设计组织身份、SSO、RBAC、节点归属、集中策略、租户隔离、合规审计、批量升级和可用性，不在当前 change 中预埋未经验证的实现。

公共 SaaS 会使平台直接承担大量用户设备的远程访问、安全、隔离、容量和运营责任，当前不规划。未来即使提供托管控制面，也必须保持数据面私有、节点所有者可撤销和本地策略最终裁决。

## 核心问题

- 用户不知道其他设备当前在线与否、运行了什么服务以及如何访问。
- 用户记不住不同设备、Docker 容器、游戏服务的地址和端口。
- 服务已经启动但远端无法访问时，用户难以判断是监听地址、端口映射、WireGuard、路由还是服务本身的问题。
- 传统面板只能展示数据，不能结合多个节点的证据自主制定诊断步骤。
- 直接让大模型操作系统风险过高，需要确定性工具、权限边界、人工审批和执行后验证。

## 标志性演示场景

用户在 Windows 节点 A 的本地面板询问：

> B 上有哪些服务？为什么 PDF 服务打不开？

Agent 应完成以下闭环：

1. 查询 B 的在线状态和 A/B WireGuard 连通状态。
2. 调用 B Agent 的端口、进程与 Docker 只读工具。
3. 识别 B 上的 PDF 容器及其监听地址。
4. 从 A 测试服务可达性，并判断它仅监听 `127.0.0.1`。
5. 基于真实工具证据解释不可访问原因。
6. 建议临时共享该服务，并说明风险、目标地址和有效时间。
7. 在用户明确批准或命中有效预授权后，由 B 执行临时共享。
8. 从 A 自动验证访问结果，生成可打开链接并记录审计事件。

第一优先级 MVP 实现步骤 1–5；步骤 6–8 作为紧随其后的安全操作 change。

## 系统分层

### AI Agent 层

- 使用用户自行提供的大模型 API 理解问题、选择工具和综合结果。
- 支持 ReAct 风格的开放式诊断循环，并设置停止条件、调用预算和超时。
- 对有副作用的任务使用 Plan → Confirm → Execute → Verify 工作流。
- 模型不可直接访问任意 Shell、Python REPL、文件系统或秘密信息。

### 上下文与记忆层

- **实时状态**：WireGuard、端口、进程、Docker、节点在线状态；通过工具按需读取，不作为长期记忆复制。
- **短期上下文**：当前对话、工具调用轨迹、诊断假设和中间结果。
- **工作流状态**：计划、待审批动作、执行结果、重试次数和验证状态。
- **长期记忆**：节点别名、用户偏好、服务身份、已确认事实和安全约束。
- 使用检索、摘要、结构化状态和动态工具选择控制上下文规模，不把完整拓扑、日志或历史对话一次性发送给模型。

### 确定性工具层

- WireGuard 状态与 peer 诊断。
- TCP/UDP 监听端口和进程枚举。
- Docker 容器、镜像和端口映射的只读查询。
- HTTP、游戏和常见协议的有限安全探测。
- 节点、服务目录和跨节点可达性查询。
- 后续增加临时服务共享、服务重启和网络配置等受审批工具。

操作权限使用确定性 L0～L4 等级，而不是由模型判断自身权限：

- **L0 只读观察**：可以在预算内自动执行。
- **L1 无副作用建议**：可以自动生成计划，但不改变系统。
- **L2 低风险可逆操作**：默认逐次批准；节点所有者可以按 peer、工具、服务、端口、持续时间和有效期建立可撤销预授权。
- **L3 敏感操作**：服务重启、容器控制和网络配置等，后续独立设计并保持更严格批准。
- **L4 禁止操作**：任意代码、秘密读取和删除未知资源等始终拒绝。

“同一人拥有两个节点”不能自动推导为无限写权限；目标节点本地策略始终拥有最终决定权，模型不能创建授权或提高等级。

### 分布式节点层

- Windows、macOS、Linux 分别运行本地 Agent Runtime。
- 本地聊天与资源面板只监听环回地址。
- 节点通过 WireGuard 私有网络交换经过认证的工具请求和状态。
- 每个节点只暴露其权限策略允许的工具；远端文本和工具结果均视为不可信输入。
- 后续由 Coordinator 提供节点注册、能力发现、策略、状态同步和网络协调。

## 产品原则

- **AI 是交互核心**：产品的主要价值是基于真实环境的推理、诊断和安全执行，而不是为传统面板附加聊天框。
- **工具确定执行**：大模型选择和组合工具，但系统观察与操作由可测试的 Python 工具完成。
- **证据驱动**：诊断结论必须引用实际工具结果，并区分事实、推测和未知信息。
- **默认只读**：MVP 的跨节点工具均为只读；有副作用能力必须单独设计和审批。
- **本地优先**：模型密钥、长期记忆和本地面板默认只存在于所属节点。
- **最小上下文**：实时状态按需检索，工具按权限和任务动态暴露，避免上下文与工具集合无界增长。
- **可降级运行**：模型不可用时，资源面板、工具和服务目录仍可工作，但明确标记 AI 能力不可用。
- **真实评估**：使用 A/B 真机任务评估工具选择、参数正确性、诊断结论、安全边界、延迟和成本。
- **保护现有网络**：首轮只读取现有 WireGuard 状态，不覆盖 `HomeMac` 或 B 的手写配置。

## 当前开发与测试基线

- **设备 A**：Windows 当前开发机，已安装官方 WireGuard 客户端，通过 `HomeMac` 隧道连接 B；本机具有 Python 3.11/3.12 环境。
- **设备 B**：家庭 macOS 设备，既是 WireGuard 服务器也是组网节点；当前使用手写配置和终端命令启停服务。
- **现有能力**：A 与 B 已经能够通过 WireGuard 互通，可以直接验证跨节点 Agent 与真实工具调用。
- **实现技术**：Python 3.11+、LangChain Agent、LangGraph 持久化工作流、结构化工具接口；MCP 是否作为跨节点工具协议需通过安全与兼容性实验决定。
- **模型配置**：用户在每个节点自行配置兼容的大模型 API，密钥只保存在本机。
- **安全护栏**：早期所有 WireGuard、端口、进程和 Docker 工具只读；自动化使用独立测试资源。

## 分阶段路线

### 阶段 0：Agent 工程与评估基线

- 建立 Python 单体仓库、类型检查、测试、三端 CI 和秘密脱敏规则。
- 建立模型 Provider 配置、结构化输出、工具 schema 和调用轨迹。
- 建立短期状态、持久化 checkpoint、上下文裁剪与基础长期记忆模型。
- 定义只读、需审批和禁止三类工具权限。
- 建立离线可重复的假模型/假工具测试，以及 A/B 真机评估集。

### 阶段 1：现有组网上的跨节点 AI Agent

- A、B 分别运行本地 AI Agent 和聊天/资源面板。
- 实现 WireGuard 状态、监听端口、进程、Docker 和服务可达性只读工具。
- 节点通过现有 WireGuard 网络发现并调用远端只读工具。
- Agent 能回答“B 有什么服务”和“为什么服务不可访问”等跨节点问题。
- 使用动态工具选择和最小上下文，避免把全部节点工具和状态放进单次提示。
- 建立工具选择正确率、参数错误率、任务完成率、诊断证据一致性、延迟和成本报告。

已完成并归档 change：`deliver-ai-agent-over-existing-mesh`。

### 阶段 2：人工审批的安全操作闭环

- 把“临时发布”明确为“临时共享本机服务”：在现有 WireGuard 私网中，为指定 peer 创建限时入口，不公开到互联网，也不修改服务本身。
- 第一条纵向切片以仅监听本机的 HTTP/HTTPS 服务为主，不隐含提供任意 TCP 转发。
- Agent 生成结构化操作计划、风险说明和预期变化。
- 默认由目标节点用户逐次批准；允许节点所有者为 L2 操作建立细粒度、可撤销、会过期的预授权。
- 授权后执行，使用幂等键、资源所有权、临时凭据和绝对过期时间控制副作用。
- 从请求节点自动验证结果；失败时回滚并保留审计记录。
- 复用同一机制临时开放远程调试面板，但增加一次性访问令牌。
- 本地页面展示计划、风险、授权依据、执行、验证、回滚和到期状态，不在本阶段重写独立 React 前端。

已完成并归档 change：`approve-and-share-local-service`。

### 阶段 2.5：统一 Prompt 与 Context Runtime

- 让所有生产模型调用经过统一、可追踪且有预算的上下文组装路径。
- 继续对话时组合近期原文、滚动摘要、动态工具、工具结果、制品引用和经确认的相关记忆。
- 固定“实时工具证据 > 已确认适用记忆 > 历史摘要 > 模型推断”的事实优先级。
- 建立最小 prompt 注册、版本、输入契约、变更记录和黄金/对抗评估。
- 将失败区分为上下文、prompt/模型、工具 Harness 和治理问题，并保持无模型时的确定性降级路径。

已完成并归档 change：`integrate-agent-context-and-prompt-runtime`。

### 阶段 3：Coordinator 与服务目录

- 节点身份注册、撤销、心跳和工具能力发现。
- 同步带新鲜度的节点与服务目录，支持节点离线和工具降级。
- 根据节点、用户权限和任务阶段动态暴露工具。
- 为跨节点请求建立认证、授权、速率限制和审计。

`coordinate-agent-network` 已在 2026-07-26 完成实现和真实 A/B 迁移验收：节点注册、撤销、
心跳、能力/服务目录、Ed25519 短期身份、动态工具复核、管理/资源视图、综合评估和 static
回退均已建立。它没有修改 WireGuard、生产 Gateway、模型端口或防火墙；下一阶段仍是独立的
自动组网 change。

### 阶段 4：自动组网与连接优化

- WireGuard 虚拟地址分配和受管配置下发。
- 点对点路径探测、状态解释和必要回退路由。
- Windows、macOS、Linux Provider 与受管资源所有权。
- 保护用户已有网络接口、密钥、路由和配置文件。

现有 `deliver-minimum-viable-mesh` change 暂停直接实施。它同时包含 Coordinator、自动 WireGuard 管理、Linux、服务目录、前端和发布任务，并与已经完成的只读 Agent MVP 存在重复；实施前应拆分为至少三个可独立验收的 change：

- `coordinate-agent-network`：节点身份、心跳、能力发现和服务目录。
- `manage-wireguard-connectivity`：受管配置、直连探测、回退和资源所有权。
- `add-linux-node-provider`：Linux 系统适配、systemd、权限和干净环境生命周期。

### 阶段 5：游戏与服务智能识别

- 建立可扩展探测器，支持 Steam A2S、Minecraft 和常见服务。
- 大模型根据确定性元数据生成名称、说明和访问建议，不读取业务正文。
- 记录识别来源、置信度和用户纠正，将确认结果写入长期服务记忆。
- 未识别服务继续以端口、进程和设备信息可靠展示。

建议 change：`add-game-and-service-intelligence`。

### 阶段 6：产品体验与可分发交付

- 抽象稳定的网络 Provider 能力并接入 n2n。
- Coordinator 支持 Docker Compose 和可重复的一键部署。
- Agent 提供 Windows、macOS、Linux 安装包、安全升级、回滚、完整卸载和校验和。
- 在不改变本地优先边界的前提下，完善节点、服务、计划、批准、操作、验证、过期和故障恢复体验；是否采用独立 React 前端由用户测试和打包约束决定。
- 完善诊断包、威胁模型、性能基线、演示视频和公开评估报告。

建议独立 change：`improve-local-product-experience`、`package-one-click-deployment`、`add-n2n-network-provider`。安装分发、前端体验和新网络 Provider 不放进同一个实现 change。

### 阶段 7：经验证的操作 Playbook

- 从已完成操作中保存结构化候选记录：适用条件、实时证据、确定性动作、验证方法、回滚方法、平台、版本和最终结果。
- 只有通过确定性验证且已脱敏的记录可以成为版本化 Playbook；一次成功不能自动升级为通用经验。
- Agent 可以使用关键词、结构化过滤或 RAG 检索候选 Playbook，但每次复用前必须重新检查实时状态、兼容性和当前授权。
- 跨节点共享时必须移除秘密和环境专属标识，记录来源、版本和验证次数；接收节点可以拒绝或重新验证。
- Playbook 不能修改程序、创建权限、扩大预授权或绕过当前目标节点策略。
- 多 Agent 可以在出现明确的规划、复核或协作价值后单独评估，不作为经验沉淀的前置条件。

建议 change：`add-verified-operation-playbooks`。该阶段排在安全操作闭环之后，当前不着急实施。

## MVP 明确非目标

- 不自动创建、修改或删除用户现有 WireGuard 配置。
- 不提供任意 Shell、Python REPL 或运行时生成代码工具。
- 不允许模型自主执行网络修改、服务重启或容器控制。
- 不扫描节点所在的整个物理局域网。
- 不实现多 Agent 辩论、角色扮演或无明确价值的复杂编排。
- 不同时实现 WireGuard 自动管理、n2n、游戏全量识别和三端安装包。
- 不用 RAG、知识图谱或多 Agent 数量作为项目完成度指标。
- 不用 prompt 长度、上下文窗口占用或所谓 Harness 层数作为项目完成度指标。
- 不实现自动 prompt 优化、自修改 Harness、通用 Agent/Harness 平台、公共 SaaS 或企业 RBAC。
- 不允许历史成功记录自动变成权限，也不允许所谓“自进化”修改程序或绕过当前授权。

## 经验证经验与多 Agent 的后续边界

- 合规、正确、完整且有执行后验证与回滚记录的操作，可以在后续 change 中抽取为版本化 Playbook 候选。
- Playbook 可以使用关键词、结构化过滤或 RAG 思路检索，但命中后必须重新读取实时状态、重新校验适用性并重新经过当前授权。
- 跨节点共享经验不共享执行权限，已成功历史不能成为自动执行或扩大预授权的依据。
- 仅在单 Agent 已出现明确角色冲突时引入多 Agent，例如计划、验证或安全审查需要独立责任；不以 Agent 数量展示复杂度。
- 上述能力不属于 `integrate-agent-context-and-prompt-runtime` 的实现范围，应按可独立评审的纵向闭环另建 change。

## 完整性与作品集标准

- A/B 真机可以重复完成标志性诊断场景。
- 陌生开发者能按 README 在合理时间内启动本地演示。
- 工具调用、模型响应、审批和执行结果具有可追踪 run ID。
- 核心 Agent 路径具有假模型单元测试和真模型评估集。
- 提供工具选择、参数正确性、任务成功、安全拦截、延迟和成本指标。
- 提供架构图、ADR、威胁模型、失败案例和三分钟演示视频。
- 清楚说明确定性代码与大模型决策的边界，以及何时选择 ReAct 或显式 LangGraph 工作流。

## OpenSpec 文档策略

- 本文件维护长期产品方向、阶段顺序和跨 change 原则。

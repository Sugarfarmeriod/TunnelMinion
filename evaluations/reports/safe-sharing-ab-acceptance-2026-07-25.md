## 结论

本轮完成了隔离部署、真实模型候选计划评测、双向连通性检查和安全清理，但没有把专用入口的

- B：macOS，`10.77.0.1`。
- 隔离 fixture：B 的 `127.0.0.1:18880`，Python 标准 HTTP 服务。
- 隔离 Gateway：先后验证 `10.77.0.1:18883` 与 `10.77.0.1:8889`。
- 临时数据和代码仅位于 B 的 `/tmp/tunnelminion-safe-sharing-*20260725`。
- A/B 使用新生成的临时 Node ID 和独立 `tmn_` 应用凭据；未复用正式 Gateway token。
- 正式 `8787` Gateway、`5984/8888` Docker 服务和 `8082` 模型全程保持监听。

2. 隔离 Gateway 在 B 上完成启动恢复并监听指定私网地址，正式 `8787` 未停止。
3. A 到 B 的既有 `8787` 与 `8082` 可达；B 到 A 的临时回调 `10.77.0.2:18900`
   返回 HTTP 200，证明请求节点验证回调方向可用。

## 未通过与安全失败

| 场景 | 结果 | 系统行为 |
|---|---|---|
| A 直连 B 隔离 Gateway `18883` | TCP 超时 | 诊断返回远端不可达；没有调用模型生成计划 |
| 改用隔离 Gateway `8889` | TCP 超时 | 同上 |
| B 本机检查隔离监听 | `LISTEN` 正常 | 证明不是应用启动失败 |
| B → A 回调 `18900` | HTTP 200 | 回调方向没有被阻断 |

该结果不能替代“创建入口 → A 验证 → 浏览器桥访问 → 到期清理”的成功证据。准确状态是：
工作流代码与离线门禁通过，当前固定环境的新增 B 入站端口未获网络策略许可。

## 完成成功链路所需选择

二选一后重新运行：

1. 节点所有者为专用 Gateway 与入口端口范围建立明确入站允许规则；或
2. 经节点所有者授权，短暂停止正式 `8787` Gateway，把该已允许端口临时用于共享入口，
   控制面经 SSH 隔离通道运行，验收后恢复原 Gateway。

TunnelMinion 自身不得自动执行以上网络修改，也不得擅自中断正式服务。

## 可重复步骤

1. 为 A/B 创建临时数据目录和独立应用 token。
2. B 启动环回 fixture，并使用 `--enable-safe-sharing` 和专用端口范围启动隔离 Gateway。
3. A 运行 `scripts/run_safe_sharing_ab_acceptance.py submit`，确认报告状态为
   `awaiting_authorization`。
4. B 本地运行 `operation-approve`，不得从 A 或聊天授权。
5. A 运行该脚本的 `execute --wait-for-expiry` 阶段；回调只把共享凭据保留在内存，
   浏览器通过 A 的环回桥访问。
6. 验证状态依次为 `succeeded`、`expired`，入口端口释放。
7. 再创建精确预授权计划，验证完整命中自动执行、任一端口或时长越界重新等待批准。
8. 注入错误凭据、端口占用、服务 PID 变化、A 回调离线、B 重启、验证失败、代理崩溃和
   所有权冲突；失败不得报告成功或误删未知资源。
9. 前后比较 WireGuard、路由、Docker、正式服务和用户配置摘要。
